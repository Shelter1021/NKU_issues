## 第一章汇编语言的基本概念 ##

**什么是编辑器、汇编器和链接器?**

答:汇编器将汇编语言代码转换为机器语言代码。链接器则是将一个或多个由汇编器生成的对象文件合并成单个可执行文件的工具。链接器处理符号解析、重定位和内存分配。

**为什么不直接把汇编语言编译成可执行的exe程序，取消中间的链接过程？**

为了支持**模块化编程**和**代码复用**，链接过程允许将程序拆分为多个独立编译的文件（以及调用现有的库函数），最后统一合并并解析地址引用，从而避免了所有代码必须写在一个文件中且每次修改都要整体重编译的低效。

！汇编语言是所有程序设计语言中**最古老**的语言；与机器语言最为接近；可以直接访问硬件；需要了解计算机体系结构和操作系统

#### 虚拟机 ####

**虚拟机的概念：**·对于每个语言层次，将其想象成一台假想的计算机(虚拟机)；高层虚拟机的程序，通过解释或者翻译的方式，在底层虚拟机上执行

**十六进制数补码**

考虑十六进制数2F4B,要计算它的补码，我们首先将每个数字位取反，再对末位加1。在十六进制中，取反可以通过用F(即15)减去每一位实现。因此：·2(即0010)取反后变为D(即1101) ；F(即1111)保持不变，因为它已经是最大值 ；4(即0100)取反后变为B(即1011) ；B(即1011)取反后变为4(即0100)；2F4B的每位取反后得到D0B4。对这个结果加1,即D0B4+1,得到D0B5。因此，2F4B的补码是DOB5。

1. 数据拆解与高低位判定

首先对十六进制数值 0x7F000001 进行字节拆解（书写顺序为左高右低）：

- **拆分**：将数据拆解为 4 个独立字节 —— `7F`, `00`, `00`, `01`。
- **高位 (MSB)**：`7F`（数值的“头部”，权重最高）。
- **低位 (LSB)**：`01`（数值的“尾部”，权重最低）。

2. 内存模型

- **物理模型**：内存可以看作是一排沿特定方向延伸的格子。
- **延伸方向**：从 **低地址** 指向 **高地址**。

3. 存储模式对比

| **模式**                       | **定义与规则**                                               | **内存中的存放图示 (低地址 → 高地址)**             |
| ------------------------------ | ------------------------------------------------------------ | -------------------------------------------------- |
| **大端字节序** (Big-Endian)    | **高位**字节存入**低地址**。 即：把数据的“头”放在内存的“头”。 | **`7F` `00` `00` `01`** *(内存顺序与书写顺序一致)* |
| **小端字节序** (Little-Endian) | **低位**字节存入**低地址**。 即：把数据的“尾”放在内存的“头”。 *(Windows/x86 常用)* | **`01` `00` `00` `7F`** *(内存顺序与书写顺序相反)* |

------

一句话核心区别：

在内存的低地址处，大端放的是高位（7F），而小端放的是低位（01）。

##### 指令（指令伪指令考） #####

指令是⼀条汇编语句。**汇编器把汇编指令翻译成对应的机器指令**

**标号**：充当**指令或数据位置标记**的标识符  分为数据标号（标识变量的地址）与代码标号（标识代码的地址）

理解：**数据标号** = 变量名（我们要操作的**物品**在哪）。    **代码标号** = 跳转点（我们要去的**目的地**在哪）

数据标号⸺count DWORD 100，指的是相对data数据段，在内存起始地址的偏移

**offset可以获取数据标号的内存偏移地址，不⽤以冒号结尾：**

```
.data
    str_hello BYTE "Hello World! ", 0
.code
    mov eax, OFFSET str_hello
```

**对应的 C 语言逻辑：**

```
// .data 部分
char str_hello[] = "Hello World! "; 

// .code 部分
char* eax = &str_hello; // 把 str_hello 的【地址】赋值给 eax
```

**逐行解释：**

1. **`.data`**：告诉计算机“下面我要定义变量了”。
2. **`str_hello BYTE ...`**：
   - 申请了一块内存。
   - 里面填入了字符 "H", "e", "l", "l", "o"... 以及结尾的 0。
   - 给这块内存的**起始位置**贴了个标签，叫 `str_hello`。
3. **`.code`**：告诉计算机“下面是代码指令”。
4. **`mov eax, OFFSET str_hello`**：
   - 请注意，这里**不是**要把字符串 "Hello..." 塞进 `EAX` 寄存器（EAX 只有 4 字节，根本装不下这么长的字符串）。
   - 而是把字符串在内存中的**门牌号（地址）**，存进 `EAX`。

所有的地址都是基于段起点的距离。OFFSET str_hello 实际上是在计算：

> `str_hello` 的位置 - `.data` 段的起始位置 = **偏移量**

这是一个语法规定，用来区分**变量**和**跳转点**。

**A. 代码标号 (Code Label) —— 需要冒号**

- **例子**：`start:` , `loop_here:`
- **作用**：它只是一个位置标记，**不占内存空间**。
- **语法**：必须加冒号，告诉编译器“这只是个路标，下面紧接着就是指令”。

**B. 数据标号 (Data Label) —— 不需要冒号**

- **例子**：`str_hello BYTE ...`

- **作用**：它定义了一个**变量**，是**占用内存空间**的。

- **语法**：

  Plaintext

  ```
  名字      类型    初始值
  str_hello BYTE   "Hello..."
  ```

  编译器看到后面跟着 `BYTE`、`DWORD` 等类型定义符，就知道前面的 `str_hello` 是一个变量名（数据标号），所以**不需要冒号**来区分。

- **`OFFSET`** 就像 C 语言里的取地址符 **`&`**。
- 我们用它是为了获取字符串的**首地址**（指针），以便后续传递给函数（比如 `printf`）去打印整个字符串。
- **数据标号不加冒号**，因为后面紧跟的类型（BYTE/DWORD）已经表明了它的身份。

让我们来看看汇编器（Assembler）是怎么“翻译”这三句话的：

**写法 (1): 字符串形式 (最常用)**

```
str_hello BYTE "Hello World", 0
```

- **解释**：这是给人类看的简写。汇编器看到双引号 `""`，会自动查 ASCII 表，把每个字母转换成对应的数字。
- **转换结果**：`48 65 6C 6C 6F 20 57 6F 72 6C 64 00`

**写法 (2): 十六进制数值形式 (最硬核)**

代码段

```
str_hello BYTE 48h, 65h, 6ch, 6ch, 6fh, ...
```

- **解释**：这是直接写出每个字节的**机器码**（ASCII码值的十六进制）。
  - `48h` = 'H'
  - `65h` = 'e'
  - `6ch` = 'l'
  - ...
- **转换结果**：`48 65 6C 6C 6F 20 57 6F 72 6C 64 00` （完全一样！）

**写法 (3): 字符列表形式**

代码段

```
str_hello BYTE 'H', 'e', 'l', 'l', 'o', ...
```

- **解释**：这是把字符串拆开写。汇编器还是会去查表，把 `'H'` 变成 `48h`，把 `'e'` 变成 `65h`。
- **转换结果**：`48 65 6C 6C 6F 20 57 6F 72 6C 64 00` （还是完全一样！）

·符号常量(或符号定义),将标识符与整数表达式或文本联系起来              符号常量不占用存储空间    变量占用存储空间

  - *缺点*：**500 是啥？** 可能是攻击力，也可能是血量，全靠猜。

  - *优点*：**语义清晰**，一眼看出这是“数量”。

1. 拒绝猜谜 (易读)

   用有意义的单词（如 COUNT）代替冷冰冰的数字（魔术数字），让代码自带注释效果，任何人都能看懂。

2. 一键换芯 (易维护)

   如果要把 500 改成 1000：

   - **不用常量**：你需要全篇搜索“500”，逐个替换（容易把无关的 500 也改错）。
   - **用常量**：只需要改第一行 `COUNT = 1000`，后面几百处引用的地方**自动全部更新**，安全又快。

**计算数组和字符串的⼤⼩**

⽤**$**运算符存储当前语句的地址偏移

**计算内存⼤⼩的话，就可以⽤str_size = ($ - str_hello)来计算**

**⽤于计算数组中的元素个数：**

dw_array DWORD 0, 1, 2, 3, 4

**array_size = ($ - dw_array)/4**

------

**`$` (Current Location Counter)**：它代表**“当前这一行代码”**在编译时所处的内存偏移地址。

- 计算逻辑：

  如果你知道**“起点”（变量名），也知道“终点”**（$，也就是刚填完数据后的位置），那么：

  > **终点 ($) - 起点 (变量名) = 这段数据占用的总字节数**

------

**场景一：计算字符串长度（字节数）**

```
str_hello BYTE "Hello", 0
str_size = ($ - str_hello)
```

内存图解：

假设 str_hello 从地址 100 开始。

| **地址** | **内容** | **备注**                  |
| -------- | -------- | ------------------------- |
| **100**  | 'H'      | <- `str_hello` (起点)     |
| 101      | 'e'      |                           |
| 102      | 'l'      |                           |
| 103      | 'l'      |                           |
| 104      | 'o'      |                           |
| 105      | 0        | (结束符)                  |
| **106**  | ...      | <- **`$` (当前就在这里)** |

**计算过程：**

1. 汇编器铺完了 "Hello" 和 0，占用了 6 个格子。
2. 此时光标（`$`）停在 **106** 号地址。
3. 计算：`106 ($) - 100 (str_hello) = 6`。
4. 所以 `str_size` 就等于 **6**（字节）。

------

**场景二：计算数组元素个数**

```
dw_array DWORD 0, 1, 2, 3, 4
array_size = ($ - dw_array) / 4
```

这里多了一个 **“除以 4”**，为什么？因为这是**双字数组**（DWORD）。

内存图解：

假设 dw_array 从地址 200 开始。

注意：每个 DWORD 占 4 个字节！

| **地址** | **内容**  | **对应数值**              |
| -------- | --------- | ------------------------- |
| **200**  | [ 4字节 ] | 0 <- `dw_array` (起点)    |
| 204      | [ 4字节 ] | 1                         |
| 208      | [ 4字节 ] | 2                         |
| 212      | [ 4字节 ] | 3                         |
| 216      | [ 4字节 ] | 4                         |
| **220**  | ...       | <- **`$` (当前就在这里)** |

**计算过程：**

1. 先算总字节：

   220 ($) - 200 (dw_array) = 20 字节。

   (虽然只有5个数，但占用了20个格子的地盘)

2. 再算个数：

   因为每个元素占 4 字节，要把“总地盘”换算成“人数”。

   20 字节 / 4 = 5 个元素。

**通用公式：**

> **元素个数 = ( $ - 数组名 ) / 单个元素的大小**

- 如果是 `WORD` (2字节)：就除以 2。
- 如果是 `DWORD` (4字节)：就除以 4。
- 如果是 `QWORD` (8字节)：就除以 8。

**TEXTEQU伪指令**
·TEXTEQU伪指令与EQU非常相似，同样可以用来创建文本宏(text macro)。

·它有三种不同的使用格式：第一种格式会将文本赋值给符号；第二种格式则将已定义的文本宏内容赋值给符号；第三种格式将整数表达式常量赋值给符号。

1. 起外号（直接文本）

   PI_STR TEXTEQU <"3.14">

   - 以后写 `PI_STR` 就等于写字符串 `"3.14"`。

2. 影分身（宏复制）

   COPY_PI TEXTEQU PI_STR

   - 把上面的宏复制一份给新名字。

3. 算术转文本（最常用）

   RES TEXTEQU %5+5

   - 先计算 `5+5=10`，再把数字 **10** 变成字符串 **"10"** 存起来。

用来定义一段可以随时修改的代码或字符串文本。

**LENGTHOF操作符**

LENGTHOF操作符计算数组中元素的数⽬，元素由出现在同⼀⾏的值定义

```
 .data
 var1 DWORD 0，1，2，3
 .code

```

`EAX` 的值会变成 4

如果你想算 `var1` 有几个元素，你得手动算汇编器占了多少字节，然后再除以每个元素的大小：

> `($ - var1) / 4` = 元素个数

**`LENGTHOF`** 直接告诉汇编器：“别跟我扯什么字节、地址，你直接告诉我逗号后面一共写了**几个数**？”

- **你的代码**：`var1 DWORD 0, 1, 2, 3`
- **数数**：
  1. `0` (第1个)
  2. `1` (第2个)
  3. `2` (第3个)
  4. `3` (第4个)
- **结果**：一共 **4** 个元素。

你给的定义里有一句很关键的话：“*元素由出现在**同一行**的值定义*”。

**注意：** 如果你换行写，而且没用逗号连起来，`LENGTHOF` 可能会“近视”，只看得到第一行。

**举个例子：**

```
.data

        DWORD 40, 50         ; 第二行（虽然物理上挨着，但没标号）

.code
mov eax, LENGTHOF myArray
```

- **结果**：`EAX` 是 **3**！(它只数了 `10, 20, 30`)。
- **原因**：因为 `40, 50` 属于下一行单独定义的 DWORD，虽然内存是连着的，但 `myArray` 这个标签默认只管它那一行的兄弟。

var1 DWORD 0, 1, 2, 3,    ; <--- 注意这个逗号！
           4, 5, 6, 7

这个EAX是8

##### 直接偏移操作数 #####

在变量名后面加上一个偏移值，可以创建直接偏移(direct-offset)操作数，·访问没有显式标号的内存  

<img src="C:\Users\xiexi\AppData\Roaming\Typora\typora-user-images\image-20251221143102251.png" alt="image-20251221143102251" style="zoom: 50%;" />

在 x86 架构中，数据是按照“小端序”存储的。这意味着**低位字节存储在低地址，高位字节存储在高地址**。

- **代码中的定义**：`var1 DWORD 1000h`
- **数值**：十六进制的 `1000h`，写成32位（DWORD）也就是 `00001000h`。
- **拆分字节**：0010 0000
- 内存中的样子（看图片下方的十六进制数据）：   地址 00403000 处显示的是：00 10 00 00。

同理，`2000h` (`00002000h`) 在内存中存储为 `00 20 00 00`。

**第一句：`mov eax, var1`**

- **含义**：从 `var1` 的起始地址（偏移+0）读取4个字节。
- **读取的字节**：`00 10 00 00`
- **CPU解释（小端序还原）**：`00001000h`
- **结果**：EAX = `1000h` (这是正常的预期值)。

**第二句：`mov eax, [var1+1]`**

- **含义**：从 `var1` 地址 **+1个字节** 的地方开始，读取4个字节。
- **读取的范围**：偏移 +1 到 +4。
- **读取的字节序列**：
  - +1: `10`
  - +2: `00`
  - +3: `00`
  - +4: `00` (注意：这是下一个变量 `2000h` 的第一个字节！)
- **组合字节**：`10 00 00 00`
- **CPU解释（小端序还原）**：
  - 低位是 `10`，高位全是 `0`。
  - 结果为 `00000010h`。
- **结果**：EAX = `10h` (十进制 16)。

**第三句：`mov eax, [var1+2]`**

- **含义**：从 `var1` 地址 **+2个字节** 的地方开始，读取4个字节。
- **读取的范围**：偏移 +2 到 +5。
- **读取的字节序列**：
  - +2: `00`
  - +3: `00`
  - +4: `00` (下一个变量 `2000h` 的低位)
  - +5: `20` (下一个变量 `2000h` 的次低位)
- **组合字节**：`00 00 00 20`
- **CPU解释（小端序还原）**：
  - 最低位 `00`
  - 次低位 `00`
  - 次高位 `00`
  - 最高位 `20`
  - 拼起来是 `20000000h`。
- **结果**：EAX = `20000000h`。

<img src="C:\Users\xiexi\AppData\Roaming\Typora\typora-user-images\image-20251221125335684.png" alt="image-20251221125335684" style="zoom:50%;" />[var1+4]

变量 `var1` 是这串数据的起始地址（门牌号）。

- 第 1 个数 (`1000h`)： 住在 `var1` 开始的 0~3 号位置。
- 第 2 个数 (`2000h`)： 紧挨着后面，住在 `var1` **+ 4** 开始的位置。
- 第 3 个数 (`3000h`)： 再往后，住在 `var1` **+ 8** 开始的位置。

##### 间接寻址 #####

⽤**寄存器**作为指针来控制该寄存器的值称为间接寻址；⼀个操作数使⽤的是间接寻址的话就称为间接操作数。

任何⼀个 32 位通⽤寄存器（EAX、EBX、ECX、EDX、ESI、EDI、EBP 和 ESP）加上**⽅括号**就能构成⼀个间接操作数。

**间接操作数**

```
.data

 .code

```

这段代码执行后，**EAX 的值是 `12345678h`**。

定义 `val dd 12345678h` 时，数据以小端序存入内存。假设 `val` 的地址是 `0x00403000`：

| **内存地址** | **偏移** | **存储的字节 (Hex)** | **对应原值的部分** |
| ------------ | -------- | -------------------- | ------------------ |
| **00403000** | +0       | **78**               | 低位 (Low byte)    |
| **00403001** | +1       | **56**               |                    |
| **00403002** | +2       | **34**               |                    |
| **00403003** | +3       | **12**               | 高位 (High byte)   |

1. **`mov esi, offset val`**
   - `ESI` 寄存器现在存放的是地址 `00403000`。
2. **`mov eax, dword ptr [esi]`**
   - 指令告诉 CPU：从 `ESI` 指向的地址开始，读取 **4 个字节 (DWORD)** 放进 `EAX`。
   - CPU 读取到的字节流是：`78 56 34 12`。
   - **关键点**：CPU 知道这是小端序机器，所以在把这 4 个字节装配进寄存器时，会把低地址的字节（78）放在寄存器的最低位，高地址的字节（12）放在最高位。

#### 堆栈机制 ####

运行时栈·

运行时栈主要有两个基本操作，压栈操作和出栈操作。

**·压栈操作**

·压栈操作是将数据元素放入栈顶的过程。在汇编语言中，这通常是通过减少栈指针ESP的值来完成的，因为栈在内存中是向下增长的。每次执行压栈操作时，栈指针首先向下移动一定数量的字节，然后将数据复制到栈指针指向的新位置上。这样可以确保后进入栈的元素始终位于栈顶，可以被最先访问和修改。

**·出栈操作**

·出栈操作是从栈中移除元素的过程，通常是指从栈顶开始。在汇编语言中，进行出栈操作时，首先从当前栈指针指向的位置读取数据，然后栈指针会增加相同的字节数，向上移动回到之前的状态。出栈操作后，原先位于栈顶的数据被移除，允许访问在此之前压入栈的下一个元素。

**使用场景**

.**函数调用与返回**：在函数调用时，返回地址和函数的参数通常被压入栈中。当函数执行完成后，通过出栈操作来恢复这些返回地址和参数，保证程序能够返回到正确的位置继续执行。

**.局部变量的存储**：函数的局部变量也经常存储在栈上。这使得每次函数调用时都有一个清晰的局部作用域，函数执行完毕后，这些局部变量可以简单地通过调整栈指针来丢弃。

.**程序执行状态的保存和恢复**：在进行诸如上下文切换这类操作时，程序的当前状态可以被保存到栈中，以便之后可以恢复到相同的状态继续执行。

##### push pop指令 #####

**1. PUSH（压栈 / 存）**

- **动作**：把数据扔到堆栈最上面。
- **底层**：`ESP` 指针**减小**（向低地址生长），然后写入数据。
- **特权**：可以压入**立即数**（常数），例如 `PUSH 100`。

**2. POP（出栈 / 取）**

- **动作**：把堆栈最上面的数据拿出来，还原到寄存器或内存。
- **底层**：先读数据，然后 `ESP` 指针**增加**（释放空间）。
- **限制**：**不能** POP 给立即数（你不能写 `POP 100`）。

**后进先出 (LIFO)**：像给弹夹压子弹，最后压进去的，最先弹出来。

- **配对使用**：有一条 PUSH，通常就得有一条 POP，否则堆栈不平衡程序会崩。

**AND指令**

·AND指令可以操作寄存器和存储单元作为目的操作数，而立即数、寄存器和存储单元可以作为源操
作数，但**目的操作数和源操作数中不能同时都是存储器操作数**。

常被用于清除选定位，保留其他位，当执行AND指令时，它**会设置标志位CF和OF为0**,根据结果按照定义来影响标志位SF、ZF和PF。

```
mov al, 00111011b   ; AL 寄存器初始值
and al, 00001111b   ; 与 00001111 进行 AND 操作
```

```
    0011 1011  (原始数据)
AND 0000 1111  (掩码/Mask)
-------------
    0000 1011  (结果)
```

- **高 4 位（左边）：** 掩码是 `0000`。因为“遇到 0 结果就是 0”，所以原始数据的高 4 位不管是什么，最后都变成了 `0000`。这就是图片里说的**“被清除”**。
- **低 4 位（右边）：** 掩码是 `1111`。因为“1 AND x = x”，所以原始数据的低 4 位保持原样（`1011` 还是 `1011`）。这就是图片里说的**“保持不变”**。

在 x86 汇编中，CPU 有一个特殊的寄存器叫 **EFLAGS（标志寄存器）**，里面存储了很多状态位。每执行一条算术或逻辑指令，这些位就会自动改变，用来告诉程序刚才运算的结果怎么样。

**A. 必定被清零的标志位 (CF, OF)**

当执行 `AND` 指令时，CPU 硬件设计决定了这两个标志位**总是会被设为 0**。

1. **CF (Carry Flag - 进位标志)**
   - **含义：** 通常用于无符号算术运算（如 ADD, SUB），表示最高位是否有进位或借位。
   - **在 AND 中：** 逻辑运算是按位进行的，不会产生进位或借位，所以 CF 总是被清零 (0)。
2. **OF (Overflow Flag - 溢出标志)**
   - **含义：** 用于有符号算术运算，表示结果是否超出了寄存器能表示的范围（比如正数加正数变成了负数）。
   - **在 AND 中：** 逻辑运算不会导致数值溢出，所以 OF 总是被清零 (0)。

**B. 根据结果变化的标志位 (SF, ZF, PF)**

这三个标志位会根据 `AND` 运算出来的最终结果（在上面的例子里是 `00001011`）来改变状态。

1. **SF (Sign Flag - 符号标志)**
   - **含义：** 记录运算结果的**最高位（MSB）**。在计算机中，最高位通常用来表示正负（0为正，1为负）。
   - **逻辑：** 如果结果的最高位是 1，SF=1（表示结果是负数）；如果最高位是 0，SF=0（表示结果是正数）。
   - *例子中：* 结果 `00001011` 的最高位是 0，所以 **SF = 0**。
2. **ZF (Zero Flag - 零标志)**
   - **含义：** 记录运算结果**是否全部为 0**。这是汇编里最重要的标志位之一，常用于 `JZ` (Jump if Zero) 等跳转指令。
   - **逻辑：** 如果结果等于 0，ZF=1（表示“是零”）；如果结果不等于 0，ZF=0（表示“不是零”）。
   - *例子中：* 结果是 `00001011` (十进制11)，不是 0，所以 **ZF = 0**。
3. **PF (Parity Flag - 奇偶标志)**
   - **含义：** 检查结果的**最低 8 位（一个字节）中，二进制位“1”的个数是偶数还是奇数**。主要用于早期通信中的错误检测。
   - **逻辑：** 如果“1”的个数是偶数，PF=1；如果是奇数，PF=0。
   - *例子中：* 结果 `00001011` 里面有 3 个“1”（奇数），所以 **PF = 0**。

- **解释：** 再次遇到 **`LE`** 后缀 (小于或等于)。
  - **判断：** 刚才的比较结果 (7) 是小于或等于 5 吗？**不是**。
  - **动作：** 条件**不满足**。
  - **结果：** 这条指令被 CPU **直接跳过**（相当于没写）。R0 的值保持不变。

核心知识点提示：

ARM 汇编最强大的地方就在于几乎所有指令都可以加后缀（如 EQ 等于, NE 不等于, GT 大于, LT 小于等）。这能避免使用大量的跳转指令，提高运行效率。

##### 5.多寄存器寻址类型（重点） #####

多寄存器寻址也称为**块拷贝寻址**

LDM（Load Multiple）多数据加载：**将多个地址上的值加载到多个寄存器上**

STM（Store Multiple）多数据存储：将多个寄存器上的值存到多个地址上

**寻址格式：**

LDM{cond} mode Rn{!}, reglist{^}

STM{cond} mode Rn{!}, reglist{^}

Rn: **基址寄存器**，存储传输数据的起始地址，Rn不能为R15

！：表示最后的地址写回到Rn中

reglist：**寄存器列表**，用“，”隔开，如{R1，R2，R3}最多16个寄存器

^：不允许在用户模式和系统模式下运行

**寻址模式：**

IA(Increase **After**)**每次传送后地址加4**，寄存器从左到右执行

STMIA R0, {R1, LR} 先存R1，再存LR

IB(Increase **Before**)**每次传送前地址加4**

DA（Decrease After）每次传送**后地址减4**

DB（Decrease Before）每次传送**前地址减4**

**LDM例子**：
MOV R1, #0x10000000 //数据传输起始地址0x10000000

**LDMIB R1！，{R0, R4-R6} // 从左向右加载**

R1地址加4，LDR R0, #0x10000004

R1地址加4， LDR R4, #0x10000008

R1地址加4， LDR R5, #0x1000000C

R1地址加4， LDR R6, #0x10000010

MOV R1, #0x10000010  // “!”，最后的地址写回R1寄存器

**核心指令拆解：`LDMIB R1!, {R0, R4-R6}`**

`LDM` 是 **Load Multiple** 的缩写。意思是：我要从内存里一次性拿好多数据，分别放到 `{ }` 里的这些寄存器（R0, R4, R5, R6）里去。

**怎么拿？ (IB = Increment Before)**

这是最关键的地方！后缀 **`IB`** 意思是 **"先加，再拿" (Increase Before)**。

- 想象 R1 是一个指针，指向内存地址。
- 每次搬运一个数据之前，先把指针 **向后移一格（+4字节）**，然后再读数据。

`!` 叫做 **回写**。

- 意思是：等这一堆数据全都搬运完了，请把 R1 最终停在的那个新地址，**保存回 R1 寄存器里**。
- 如果不加 `!`，R1 在搬运完后会变回原来的 `0x10000000`。

初始状态：R1 = 0x10000000

我们要搬运 4 个寄存器的数据：R0, R4, R5, R6。

因为是 **IB (先加后取)**，过程如下：

1. **处理第一个寄存器 R0：**
   - **先加：** R1 的地址先 +4 $\rightarrow$ 变成 `0x10000004`
   - **后取：** 从 `0x10000004` 这个地址拿数据，放入 **R0**。
2. **处理第二个寄存器 R4：**
   - **先加：** 地址再 +4 $\rightarrow$ 变成 `0x10000008`
   - **后取：** 从 `0x10000008` 这个地址拿数据，放入 **R4**。
3. **处理第三个寄存器 R5：**
   - **先加：** 地址再 +4 $\rightarrow$ 变成 `0x1000000C`
   - **后取：** 从 `0x1000000C` 这个地址拿数据，放入 **R5**。
4. **处理第四个寄存器 R6：**
   - **先加：** 地址再 +4 $\rightarrow$ 变成 `0x10000010`
   - **后取：** 从 `0x10000010` 这个地址拿数据，放入 **R6**。
5. **收尾 (因为有 `!`)：**
   - 把刚才最后算出来的地址 `0x10000010` 更新给 R1。
   - 现在的 **R1 = `0x10000010`**。

- **IA (先取后加)：** 如果是 `LDMIA`，R0 会直接从 `0x10000000` (原始地址) 拿数据，拿完地址再+4。
- **IB (先加后取)：** 本例是 `LDMIB`，所以 R0 **跳过了** 原始地址 `0x10000000`，是从 `0x10000004` 开始拿的。

LDMIA就是IA，先放内存，再加值，所以应该是R6应该是0x1000000C，最后的地址写回R1，为0x10000010

| **对象**          | **地址值**     | **解释**                                   |
| ----------------- | -------------- | ------------------------------------------ |
| **R6 的数据地址** | **0x1000000C** | 这是实际上读取数据的最后一个位置。         |
| **R1 的最终值**   | **0x10000010** | 这是指针更新后的位置（指向 R6 后面一格）。 |

| **步骤**  | **IA (先用后加)**           | **IB (先加后用)**            |
| --------- | --------------------------- | ---------------------------- |
| **第1步** | 拿地址0的数据，R1变成4      | R1变成4，拿地址4的数据       |
| **第2步** | 拿地址4的数据，R1变成8      | R1变成8，拿地址8的数据       |
| **第3步** | 拿地址8的数据，R1变成C      | R1变成C，拿地址C的数据       |
| **第4步** | 拿地址C的数据，**R1变成10** | **R1变成10**，拿地址10的数据 |

**最终的 R1 值：** 两个都是 **0x10**。因为不管怎么折腾，都一共加了 4 次，也就是 $4 \times 4 = 16$ (即 16进制的 10)。

**数据的区别：**

- **IA** 的数据存放在 `00, 04, 08, 0C`。
- **IB** 的数据存放在 `04, 08, 0C, 10` (整体往后挪了一格)。

**STM**例子

MOV R1, #0x10000000 //数据传输起始地址0x10000000

MOV R4, #0x10

MOV R5, #0x20

MOV R6, #0x30

STMIB R1, {R4-R6} //从左向右加载

相当于R1地址加4，STR R4, 0x10000004

R1地址加4，STR R5, 0x10000008

R1地址加4，STR R6, 0x1000000C

R1的值是#0x10000000 

**没有 `!` 就意味着“不回写” (No Write-back)。** 虽然 CPU 在内部计算时确实算出了 `0x10000004`, `0x10000008` 等地址来存放数据，但它**不会**把最后算出来的地址更新回 R1 寄存器。

所以指令执行结束后，**R1 依然保持初始值 `#0x10000000` 不变**。

<img src="C:\Users\xiexi\AppData\Roaming\Typora\typora-user-images\image-20251223205320653.png" alt="image-20251223205320653" style="zoom:50%;" />在赋值之前减4，所以R4是08，R5是04，R6是00，R1也是00，先赋值

**指令：** `STMDB R1!, {R4-R6}`

- **Initial R1:** `0x1000000C`
- **DB (Decrement Before):** 每次操作**前**，地址先减 4。
- **`!` (Write-back):** 最终地址写回 R1。
- **寄存器列表:** R4, R5, R6 (共 3 个)。

$$最终地址 = 初始地址 - (寄存器数量 \times 4)$$

$$R1 = 0x1000000C - (3 \times 4)$$

$$R1 = 0x1000000C - 0xC = 0x10000000$$

**答案：R1 的值为 `0x10000000`**。

这里有一个**ARM 的黄金法则**，一定要背下来：

> **无论堆栈是向上长还是向下长（IA, IB, DA, DB），在内存里，永远是“小寄存器（R4）在低地址，大寄存器（R6）在高地址”。**

我们来模拟过程（DB = 先减后存）：

1. **起始指针**在 `...0C`。
2. **第一步：** 地址先减 4 $\rightarrow$ `...08`。存放 **R6** (最大的寄存器先入栈，占高位)。
3. **第二步：** 地址再减 4 $\rightarrow$ `...04`。存放 **R5**。
4. **第三步：** 地址再减 4 $\rightarrow$ `...00`。存放 **R4**。

**答案：R5 存储在 `0x10000004`。**

##### 6.栈寻址（重点） #####

存储空间中的栈与寄存器组之间的批量数据传输     使用**R13（SP）**作为栈指针，指向栈顶     先进后出FILO方式访问

基本指令：LDM/STM

栈指针位置

**FULL**：栈指针指向栈顶元素（即最后一个入栈的数据元素）时称为FULL栈

**EMPTY**：栈指针指向与栈顶元素相邻的一个可用单元时称为EMPTY栈

栈增长方向

**Descending**：当数据栈向内存地址减小的方向增长时，称为Descending栈

**Ascending**：当数据栈向内存地址增加的方向增长时，称为 Ascending栈

栈的4种管理方式

FD （Full Descending Stack） ：满递减栈，数据入栈**前栈指针减4**

FA（Full Ascending Stack）：满递增栈，数据入栈**前栈指针加4**

ED （Empty Descending Stack） ：空递减栈，数据入栈**后栈指针减4**

EA （Empty Ascending Stack） ：空递增栈，数据入栈**后栈指针加4**

**D (Descending) 递减：** 栈从 **高地址** 向 **低地址** 生长。

- 入栈（Push）时，地址变小。

**A (Ascending) 递增：** 栈从 **低地址** 向 **高地址** 生长。

- 入栈（Push）时，地址变大。

**F (Full) 满栈：** SP 指针永远指向 **刚刚放入的那个数据**（即栈顶的有效数据）。

- 意味着：这里“满了”，有数据。
- **动作：** 必须 **先改指针，后放数据** (或者反过来，取决于生长方向，总之指针最终停在数据上)。

**E (Empty) 空栈：** SP 指针永远指向 **下一个准备放入数据的空位**。

- 意味着：这里是“空的”，随时可以放。
- **动作：** 先放数据，后改指针。

> **x86 的情况：** x86 的 `ESP` 指针总是指向栈顶的那个**真实数据**。当你执行 `POP` 时，它是直接把 ESP 指向的数据拿出来。**所以是 F。**

**LDMFA**

  - 从内存读取数据到寄存器。在堆栈的语境下，这就是 **出栈 (POP)**。
- **F (Full) 满栈**:
  - SP 指针指向的是 **“最后一个有效数据”**（有人的椅子）。
  - 这意味着：**要出栈，得先读数据，再移动指针。**
- **A (Ascending) 递增**:
  - 堆栈生长时，地址是 **变大** 的（向上长）。
  - 这意味着：**入栈是 +，那么出栈（反悔）就必须是 -（减）。**

因为是 F（先读），又因为是 A 的逆操作（要减），所以 LDMFA 在机器底层实际上执行的是 “**先读数据，后减地址**”。

这正好对应了 ARM 指令集中的 **`LDMDA` (Load Multiple Decrement After)**。

- **指令：** `LDMFA SP!, {R2-R4}`
  - 意思是：把栈里的数据弹出来，填满 R2, R3, R4。
- **步骤分解：**
  1. `R2 <- mem32[SP]`：先把 SP 指向的数据读进 R2。
  2. `SP地址减4`：指针往下移一格（Decrement）。
  3. `R3 <- mem32[SP]`：读取新位置的数据给 R3。
  4. `SP地址减4`：指针再往下移。
  5. ...以此类推。

DOS Header（DOS 文件头）和 PE Header（PE 文件头）是 **“引导与被引导”** 的关系，可以打个比方：DOS Header 就像是一个“路标”，它告诉操作系统：“真正的 PE 文件头在什么位置”。

1. **结构位置关系：DOS 头在前，PE 头在后**

- **DOS Header**：位于整个文件的**最开始**（偏移量 0 处）。每个 PE 文件都必须以它开头。
- **PE Header**：紧跟在 **DOS Stub**（DOS 存根）之后。

**2. 关键连接点：`e_lfanew` 字段**

DOS Header 中最重要的字段是最后一个字段 `e_lfanew`（位于 DOS 头偏移 `0x3C` 处）。

- **作用**：它存储了一个数值，这个数值就是 **PE Header 在文件中的偏移地址**。

- 寻址公式：

  PE Header 的地址 = 基地址 (ImageBase) + DOS Header->e_lfanew

3. **为什么要有这种关系？（兼容性）**

- **历史原因**：Windows 早期为了兼容 MS-DOS 系统，设计了这种结构。

[ DOS Header (含 e_lfanew 指针) ] -> [ DOS Stub ] -> [ PE Header (被 e_lfanew 指向) ] -> [ 节表 ] -> [ 数据/代码 ]

所以，**DOS Header 是进入 PE Header 的“入口”**。如果你把 DOS Header 里的 `e_lfanew` 改坏了，Windows 就找不到 PE 头，程序也就废了。

**1. Name（8 BYTE）：块名/节名**

- **图片标注：** ①
- **十六进制值：** `2E 74 65 78 74 00 00 00`
- **解读：**

  - `2E` = `.`

  - `65` = `e`
  - `78` = `x`
  - `74` = `t`
  - 后面填充了 `00`（Null-padded）。
  - **结论：** 这个节的名字是 **`.text`**，通常存放程序的执行代码。

**2. VirtualSize（DWORD）：内存中大小**

- **图片标注：** ②
- **十六进制值：** `9A 01 00 00`
- **解读：**
  - 由于x86架构是**小端序（Little Endian）**，读取时需要反转字节顺序。

**3. VirtualAddress（DWORD）：内存起始偏移 (RVA)**

- **图片标注：** ③
- **十六进制值：** `00 10 00 00`
- **解读：**
  - 小端序读取为：`0x00001000`。
  - **含义：** 这个节加载到内存后，它的起始地址相对于基址（Image Base）的偏移量是 **0x1000**。

**4. SizeOfRawData（DWORD）：硬盘中大小 (文件对齐后)**

- **图片标注：** ④
- **十六进制值：** `00 02 00 00`
- **解读：**
  - 小端序读取为：`0x00000200`。
  - **含义：** 该节在磁盘文件中实际占用的空间是 **0x200 (512字节)**。

**5. PointerToRawData（DWORD）：硬盘中偏移**

- **图片标注：** ⑤
- **十六进制值：** `00 04 00 00`

**文件偏移与虚拟内存地址转换**

Image（映像）

PE文件加载到内存时，不会原封不动地加载   根据节表的定义加载

PE文件与内存中的Image具有不同的形态

文件被映射到内存中时，**MS-DOS头部、PE文件头和节表的偏移位置与大小均没有变化**

各节被映射到内存中后，其偏移位置就发生了**变化**

RVA to RAW

$RVA（相对虚拟地址） = \text{虚拟地址(VA)} - \text{基址(ImageBase)}$ 

RAW（**文件偏移地址** /**物理地址** ） – PointerToRawData（**节在文件中的起始偏移量** ） = RVA – VirtualAddress（节在内存中的起始 RVA）

RAW = RVA – VirtualAddress + PointerToRawData

这个版本的核心逻辑是：**“不管是在内存还是硬盘，我在节里的位置（偏移）是不变的。”**

$$\text{RAW (文件地址)} = \underbrace{\text{PointerToRawData}}_{\text{文件里的起点}} + \underbrace{(\text{RVA} - \text{VirtualAddress})}_{\text{节内偏移量}}$$

> **文件地址 = 文件起点 + ( 内存地址 - 内存起点 )**

$$\text{RAW} = \text{RVA} - \underbrace{\text{VirtualAddress}}_{\text{减去：内存基址}} + \underbrace{\text{PointerToRawData}}_{\text{加上：文件基址}}$$

> “去掉内存的头，换上文件的头。”
>
> (把内存的基地址减掉，变成纯粹的偏移，再把文件的基地址加上去。)

INT（Import Name Table导入名称表）, IAT（Import Address Table）

简单来说，它的作用是**告诉操作系统程序想要调用哪些函数**。

以下是 INT 和 IAT 的详细对比和关系解析：

- **全称**：Import Name Table（导入名称表）。
- **存储位置**：在 `IMAGE_IMPORT_DESCRIPTOR` 结构中，由 **`OriginalFirstThunk`** 字段指向 1。
- **内容**：它是一个包含 RVA（相对虚拟地址）的数组，这些 RVA 指向 **`IMAGE_IMPORT_BY_NAME`** 结构（即存储了具体**函数名称**字符串的地方）2222。
- **作用**：它是一个**“备份名单”**。无论程序是否被加载到内存，INT 里的内容通常**不会改变**，始终保存着函数名，供系统加载器（Loader）查阅。

**INT 与 IAT 的关系（重点）**

在 PE 文件被加载到内存**之前**（即还在硬盘上时），INT 和 IAT 的内容几乎是一模一样的 ：

- **INT (OriginalFirstThunk)** $\rightarrow$ 指向函数名
- **IAT (FirstThunk)** $\rightarrow$ 指向函数名

**但是**，当程序被加载到内存**之后**：

- **INT**：**保持不变**，依然指向函数名。系统加载器（Loader）会读取 INT，拿到函数名（例如 "MessageBoxA"）。
- **IAT**：**会被修改**。加载器利用从 INT 拿到的名字，去动态链接库（DLL）里找到该函数在内存中的真实地址，然后把这个**真实地址**填写到 IAT 中 。

- **INT (导入名称表)**：是**“点菜单”**，写着你要吃什么菜（函数名）。这张单子是固定的，用于查找。
- **IAT (导入地址表)**：是**“上菜桌”**。最开始它也是点菜单，但程序运行后，操作系统会把真正的“菜”（函数的内存地址）端上来覆盖掉原来的单子。程序运行时，CPU 是直接去 IAT 里拿地址跳转的。

 **PE 文件导出表（Export Table）如何查找函数地址** 的逻辑图

**“通过三个表格的接力，把函数名转换成函数地址”**。

为了让您看懂，我们可以把这个过程比喻成 **“去图书馆通过书名找书”** 的过程。

在导出表结构（`IMAGE_EXPORT_DIRECTORY`）中，有三个最重要的指针，它们指向了三个数组：

1. **函数名称表** (`AddressOfNames`)：存的是 **“书名”**（函数名字符串的地址）。
2. **序号表** (`AddressOfNameOrdinals`)：存的是 **“索书号”**（函数的内部编号/索引）。
3. **函数地址表** (`AddressOfFunctions`)：存的是 **“书的位置”**（函数的真实代码地址，即 EAT）。

这张图画的就是 **`GetProcAddress`** 函数的工作原理。假设我们要找一个叫 `"MyFunc"` 的函数，流程如下 ：

- **第一步：查名字（定位 Name）**
  - 系统先去 **“函数名称表”** (`AddressOfNames`) 里，从头开始一个一个比对字符串。
  - 假设在第 **3** 个位置（下标索引为 2）找到了 `"MyFunc"`。
  - 这时候我们记下这个位置：**索引 Index = 2**。
- **第二步：找序号（Name $\rightarrow$ Ordinal）**
  - 拿着刚才得到的 **索引 Index = 2**，去查 **“序号表”** (`AddressOfNameOrdinals`)。
  - 读取序号表中第 **2** 项的数据。假设读到的数值是 **5**。
  - 这个 **5** 就是函数在地址表里的真正编号（Ordinal）。
- **第三步：拿地址（Ordinal $\rightarrow$ Address）**
  - 拿着 **序号 Ordinal = 5**，去查最后的 **“函数地址表”** (`AddressOfFunctions`)。
  - 直接找到地址表中的第 **5** 项。
  - 这里面存的值（比如 `0x1005`），就是 `"MyFunc"` 在内存中的真正起始地址。
- **第四步：调用**
  - 程序拿到这个地址后，就可以 `call` 进去执行代码了。

图中的箭头展示了 名字索引 $\rightarrow$ 查序号表 $\rightarrow$ 得到序号 $\rightarrow$ 查地址表 $\rightarrow$ 得到函数地址 的完整接力过程。

在 x86 架构（32位系统）中，栈的一个最重要特性是 **“向低地址扩展”**（Grows Downwards）。

- **入栈（PUSH）**：栈顶指针（ESP）会**减小**（往低地址移动）。
- **出栈（POP）**：栈顶指针（ESP）会**增加**（往高地址移动）。

- 所以，执行一次 Push，ESP 的值就要 **减去 4**。

$$0019FA80 - 4 = 0019FA7C$$

**1. 核心区别：观察 `CALL` 指令后的操作**

在 x86 汇编中，函数调用前都会通过 `PUSH` 指令将参数压入栈中。**区分的关键在于：函数调用结束（`CALL`）之后，是谁把这些参数占用的栈空间清除掉？**

**情况 A：调用者平栈（Caller Clean-up） -> `__cdecl**`**

这是 C/C++ 默认的调用约定，特别是对于**参数个数不确定**的函数（如 `printf`, `sprintf`），必须使用这种方式。

1. 连续执行了多个 push 指令压入参数。
2. 执行 call _sprintf 调用函数。
3. 关键特征：紧接着执行了 add esp, 10h。

- **解析**：
  - `add esp, 10h` 的意思是手动将栈指针向高地址移动 16 个字节（10h = 16d）。
  - 这说明**调用者（主程序）**正在手动清除刚才压入的参数（假设压入了4个参数，每个4字节，共16字节）。
  - **结论**：这是典型的 **`__cdecl`** 调用约定。PPT中提到：“主函数负责清除参数”

**情况 B：被调函数平栈（Callee Clean-up） -> `__stdcall**`**

这是 Win32 API（Windows系统函数）标准的调用约定。

1. 连续执行了多个 push 指令压入参数。
2. 执行 call ds:SetFilePointer 调用函数。
3. 关键特征：call 指令之后，没有 add esp 指令，而是直接执行下一条逻辑指令（如 mov ebx, eax）。

- **解析**：
  - 主程序不需要自己动手修整栈指针，说明**被调用的函数（SetFilePointer）**在内部返回时，已经通过 `RETN X` 指令顺便把参数清理掉了。
  - **结论**：这是典型的 **`__stdcall`** 调用约定。PPT中提到：“被调用函数负责清除参数” 2。

**A. 全局变量**

- **识别特征**：**硬编码的内存地址** (Hardcoded Memory Address)。

- **汇编代码分析**：

  ```
  mov eax, dword_40CF60   ; 从绝对地址 0x40CF60 取值
  add eax, dword_40C000   ; 加上绝对地址 0x40C000 的值
  mov dword_40CF60, eax   ; 将结果写回绝对地址
  ```

- 原理：

  全局变量在编译时就被分配了固定的内存地址（通常位于数据段 .data 或 .bss）。无论程序运行到哪里，这个变量的地址永远是固定的（例如 0040CF60）。PPT Source 426 的示例代码也印证了这一点 。

- 如何一眼识别：

  看到操作数是类似 **dword_4xxxxx** 或者具体的十六进制数值地址（如 0x401000），而不是寄存器加减偏移，那就是全局变量。

**B. 局部变量**

- **识别特征**：**基于栈帧指针 (EBP) 的相对寻址**。

- **汇编代码分析**：

  ```
  mov dword ptr [ebp-4], 0  ; 将 0 存入 EBP 减 4 的位置
  mov dword ptr [ebp-8], 1  ; 将 1 存入 EBP 减 8 的位置
  ...
  mov ecx, [ebp-4]          ; 读取 EBP 减 4 位置的值
  ```

- 原理：

  局部变量存储在栈 (Stack) 中。函数的栈帧由 EBP 寄存器标记基准位置。

  - `[ebp + xx]` 通常是**函数参数**（Parameters）。

  - [ebp - xx] 通常是局部变量（Local Variables）。

    PPT Source 427 的示例代码明确展示了通过 [ebp-4] 访问局部变量的方式 。Source 314 也提到局部变量存储在栈中 。

- 如何一眼识别：

  看到操作数是 [ebp - 数值] （例如 [ebp-4], [ebp+var_8]），这就是局部变量。

**简单记忆法：**

- 看到 **具体的长地址**（如 `40xxxx`） $\rightarrow$ **全局变量**
- 看到 **`EBP` 减去一个数** $\rightarrow$ **局部变量**

## 第十二章动态调试分析技术（重定位    断点） ##

**静态逆向分析面临的挑战**

无法处理代码混淆与加壳

加壳保护：二进制文件是 “壳代码”（如 UPX、VMProtect、Themida），而非真实业务逻辑。静态分析只能看到壳的解压 / 解密代码，无法还原被保护的核心功能；

代码混淆：通过控制流平坦化（Control Flow Flattening）、虚假分支插入、字符串加密、指令替换等方式，破坏代码的逻辑结构。

#### 动态逆向分析 ####

动态逆向分析（Dynamic Reverse Engineering）是在可控环境中运行目标程序（如恶意代码、软件漏洞），通过监控其运行时行为、内存状态、系统交互等方式，还原程序真实逻辑与功能的逆向技术。 

其核心区别于静态分析的 “**不运行程序**”，而是以 “**执行 + 监控**” 为核心，精准弥补静态分析的缺陷，是恶意代码分析、漏洞挖掘、软件逆向等场景中不可或缺的关键技术。

| **对比维度** | **静态逆向分析**                                | **动态逆向分析**                                     |
| ------------ | ----------------------------------------------- | ---------------------------------------------------- |
| 核心方式     | 不运行程序，分析二进制 / 汇编代码               | **运行**程序，**监控**内存 / 行为 / 系统交互         |
| 优势         | 可深度还原代码结构、无运行风险                  | 还原真实执行逻辑、捕获运行时数据                     |
| 缺陷         | 无法处理加壳 / 混淆、依赖运行时环境、控制流断裂 | 难以覆盖所有分支、运行时易触发反调试、分析效率较低   |
| 典型工具     | **Binary Ninja**、IDA Pro、Ghidra               | **x64dbg**、ollydgb、GDB、Frida、Pin                 |
| 适用场景     | 代码结构梳理、初步扫描、静态特征提取            | 加壳程序脱壳、恶意行为捕获、漏洞验证、运行时数据获取 |

动态分析技术中，最重要的是调试器：**用户模式的调试器**、内核模式的调试器

调试用户模式的应用程序：**CPU Ring3级**   x64dbg

内核模式调试器：调试操作系统内核程序   **CPU Ring0级**    WinDbg    需要双系统

题目分析：

**相对地址**：指令中包含的是偏移量（Offset）。无论程序被加载到内存的哪个位置（Image Base 是多少），这个偏移量都是固定的，**不需要重定位** 。

**绝对地址**：指令中包含的是硬编码的完整内存地址。如果程序加载基址改变，这个地址必须被修改（重定位），否则会指向错误的位置 。

- ✅ **A. `[ebp + var_8]`**

  - **类型**：栈基址相对寻址（Base Relative）。
  - **解析**：这是通过 `EBP` 寄存器加上一个偏移量（`var_8`，通常是 `-8`）来访问局部变量。这个偏移量 `-8` 是相对于栈帧基址的，无论程序运行在内存的哪里，局部变量相对于 `EBP` 的位置永远不变。因此，它不需要重定位，属于**相对地址**。

- ✅ **B. `[ebp + var_4]`**

  - **类型**：栈基址相对寻址（Base Relative）。
  - **解析**：同 A 选项。这是访问另一个局部变量，偏移量是固定的（例如 `-4`）。它不依赖于程序的加载基址，因此也是**相对地址**。

- ✅ **C. `jnz loc_0040120`**

  - **类型**：指令指针相对寻址（IP Relative）。
  - **解析**：`jnz`（跳转指令）在机器码中存储的是**目标地址与当前指令地址之间的差值**（偏移量）。无论代码段被加载到哪里，这两个指令之间的距离是恒定的。因此，它不需要重定位，属于**相对地址**。

- ❌ **D. `dword_40CF60`**

  - **类型**：直接寻址（Absolute Direct Addressing）。

    **解析**：指令 `mov eax, dword_40CF60` 中包含了一个具体的数值 `0x40CF60`。这是一个硬编码的全局数据地址。如果程序原本的基址是 `0x400000`，但被重定位到了 `0x500000`，这个地址必须被修正为 `0x50CF60` 才能正确访问数据。因此，它是**绝对地址**，受重定位影响 4444。

##### 硬件断点 #####

•不需要将CPU指令⾸字节修改为"CC"

• 基于CPU中断DRx寄存器设置

硬件断点分为三类：1.硬件执行断点2.硬件读取断点3.硬件写入断点

**硬件执行断点**

实现方式：将断点的内存地址存储到CPU的DRx寄存器

CPU执行过程中会判断下一条指令的地址与DRx寄存器中的地址是否一致

如果一致，CPU产生异常，中止程序执行，将控制权转移给调试器

**优点**：隐蔽性强，不修改CPU指令，更难检测到         

速度快，在CPU内部进行判断

**缺点**：只有4个CPU寄存器存储断点地址，DR0到DR3          

所有硬件断点共享4个DRx寄存器，包括后面介绍的硬件读取/写入断点

**硬件写入/读取断点**

硬件断点除了可以在特定指令被执行时触发，还可以在特定字节被读取时触发

可以用于发现内存中的数据何时被修改

这样的断点我们成为硬件写入断点或者硬件读取断点

硬件写入/读取断点可以设置触发条件为读取/写入/执行硬件

写入/读取断点可以设置大小位1/2/4字节

#### **菜单功能限制** ####

通常试用版的软件，菜单或窗口中的部分选项是灰色的，无法使用。

有两种可能

第⼀种是：试⽤版和正版软件是两个完全不同的⽂件（推荐使⽤）

第⼆种是：试⽤版和正版软件是同⼀个⽂件

将软件菜单和窗口变灰(不可用状态)，可以使用如下函数：EnableMenuItem函数  EnableWindow函数

**EnableMenuItem()函数**

允许或禁止指定的菜单条目，原型如下

BOOL EnableMenuItem(HMENU hMenu, UINT uIDEnableItem, UINT uEnable)

hMenu:菜单句柄

uIDEnableItem:允许或禁止的一个菜单条目的标识符

**uEnable：控制标志**

返回值：返回菜单项以前的状态

**EnableWindow()函数**

允许或禁止指定窗口,原型如下

BOOL EnableWindow(HWND hWnd, BOOL bEnable)

hWnd:窗口句柄

bEnable:  "TRUE”为允许，"FALSE”为禁止

返回值:非0表示成功，0表示失败

#### KeyFile保护 ####

KeyFile也叫注册⽂件，是⼀种利⽤⽂件来注册软件的保护⽅式， 包含加密或者未加密的数据

试⽤版的软件⼀般没有KeyFile

⽤⼾向作者付费后，会收到作者提供的KeyFile

将KeyFile放⼊指定的⽬录就可以完成注册



采用较大的KeyFile文件

加入垃圾信息，干扰逆向分析

KeyFile的合法性检查分成几部分，分散在软件的不同模块中进行判断。



KeyFile数据处理也要尽可能采用复杂的运算

可以让注册文件中的部分数据和软件中的关键代码或数据发生关联，使软件无法被暴力破解



 KeyFile是一个文件，因此，所有与Windows文件操作有关的API函数都可作为动态跟踪破解的断点。CreateFile  FindFirstFile   ReadFile  SetFilePointer
